# 一、最核心的实时系统知识

## 1. 实时系统关注的不是平均速度，而是最坏执行时间

1 kHz EtherCAT 循环意味着：

[
T_{\text{cycle}}=1\text{ ms}
]

实时线程中的一次完整循环必须满足：

[
T_{\text{receive}}+
T_{\text{update}}+
T_{\text{send}}+
T_{\text{other}}
<1\text{ ms}
]

真正需要关注的是：

- Worst-Case Execution Time，最坏执行时间，WCET
- Deadline Miss，截止时间违约
- Jitter，周期抖动
- Maximum Latency，最大延迟

即使打印操作平均只需要 0.2 ms，只要偶尔出现一次 5 ms、20 ms 的阻塞，就可能造成：

- EtherCAT 报文未按时发送；
- 从站 watchdog 触发；
- `offline_count` 增长；
- 电机进入保护或状态机异常；
- 策略输出仍在变化，但执行器不再正常跟随。

因此，“每 200 个周期才打印一次”并不能证明安全。实时系统判断的是：

> 这次操作最坏情况下会阻塞多久，而不是它多久调用一次。

这是实时开发中最重要的思维转变。

------

## 2. 实时线程中不能做不可控延迟操作

实时线程中通常应避免：

- `printf`、`std::cout`、`fprintf`
- `fflush`
- 文件读写
- 网络通信
- 动态内存分配
- `new`、`delete`
- 容器扩容
- 普通互斥锁
- 条件变量等待
- DNS 查询
- 非必要系统调用
- 可能触发缺页异常的内存访问

这不代表这些函数一定慢，而是它们的耗时通常**没有确定上界**。

例如：

```cpp
printf("motor status\n");
fflush(stdout);
```

可能涉及：

1. glibc 内部格式化；
2. 获取 `stdout` 内部锁；
3. 调用 `write()`；
4. 进入 Linux TTY 驱动；
5. 写入伪终端；
6. 唤醒终端模拟器；
7. 终端重新渲染；
8. 输出缓冲区不足时阻塞。

因此，`printf()` 可以是 thread-safe，但不是 real-time-safe。

这三个概念要严格区分：

| 概念              | 含义                             |
| ----------------- | -------------------------------- |
| Thread-safe       | 多线程调用不会破坏内部状态       |
| Async-signal-safe | 可以在信号处理函数中调用         |
| Real-time-safe    | 执行时间有足够明确、可接受的上界 |

`printf()` 通常具有一定线程安全保证，但不具有实时安全保证。

------

## 3. `fflush(stdout)` 为什么尤其危险

`fflush(stdout)` 会强制把用户态缓冲区内容写向底层输出设备。

如果输出端是：

- 真实终端；
- SSH 伪终端；
- Docker 日志管道；
- systemd journal；
- 已接近写满的 pipe；
- 处理速度较慢的日志消费者；

那么 `fflush()` 可能阻塞。

而清屏操作一般还会输出 ANSI escape sequence，例如：

```cpp
printf("\033[2J\033[H");
```

终端不仅需要接收字符，还需要执行清屏、光标移动和重新渲染。因此，清屏刷新往往比简单追加一行更容易产生显著延迟。

# 二、Linux 线程调度中的高频知识

## 4. `SCHED_FIFO` 与普通 Linux 线程不同

Linux 常见调度策略包括：

- `SCHED_OTHER`：普通分时调度；
- `SCHED_BATCH`：批处理任务；
- `SCHED_IDLE`：极低优先级；
- `SCHED_FIFO`：实时先进先出；
- `SCHED_RR`：实时时间片轮转。

EtherCAT 周期线程通常会尝试使用：

```cpp
SCHED_FIFO
```

在 `SCHED_FIFO` 下：

- 高优先级线程可以持续运行；
- 低优先级普通线程无法抢占它；
- 同一优先级线程按照 FIFO 方式调度；
- 若线程不阻塞、不休眠、不主动让出 CPU，可能长期占用核心。

因此，实时线程本身也必须有明确的周期等待机制，不能写成无限忙循环。

------

## 5. `pthread_setschedparam()` 的错误处理方式

这是非常高频、也容易写错的 Linux/POSIX 知识点。

`pthread_setschedparam()` 返回的是错误码本身，而不是简单依赖全局 `errno`：

```cpp
sched_param param{};
param.sched_priority = priority;

int rc = pthread_setschedparam(
    pthread_self(),
    SCHED_FIFO,
    &param
);

if (rc != 0) {
    fprintf(stderr,
            "pthread_setschedparam failed: %s\n",
            std::strerror(rc));
}
```

不建议仅写：

```cpp
if (pthread_setschedparam(...) != 0) {
    perror("pthread_setschedparam");
}
```

因为很多 `pthread_*` 函数直接返回错误编号，未必按照普通系统调用的方式设置 `errno`。

常见错误包括：

- `EPERM`：没有设置实时调度策略的权限；
- `EINVAL`：优先级无效或策略参数不合法；
- `ESRCH`：指定线程不存在。

------

## 6. 为什么 `SCHED_FIFO` 经常设置失败

普通用户设置实时调度策略，通常需要：

- root 权限；
- `CAP_SYS_NICE` capability；
- 合适的 `RLIMIT_RTPRIO`；
- systemd service 中允许实时优先级。

可以检查：

```bash
ulimit -r
```

查看当前用户允许使用的最大实时优先级。

也可以检查进程：

```bash
chrt -p <pid>
```

查看实际调度策略和优先级。

代码中最好在设置后再次验证：

```cpp
int actual_policy = 0;
sched_param actual_param{};

int rc = pthread_getschedparam(
    pthread_self(),
    &actual_policy,
    &actual_param
);

if (rc == 0) {
    std::cout
        << "policy=" << actual_policy
        << ", priority=" << actual_param.sched_priority
        << '\n';
}
```

原因是：

> 程序提出了设置请求，不代表设置一定已经成功。

------

## 7. 监控线程不能意外继承实时策略

普通监控线程应使用：

```text
SCHED_OTHER
```

并保持低优先级。

需要注意，POSIX 线程创建时存在调度属性继承问题。如果监控线程恰好由实时线程创建，且使用继承调度参数的默认行为，它可能继承不合适的调度策略。

因此，工程上更稳妥的做法是：

- 从普通初始化线程创建监控线程；
- 或显式配置 `PTHREAD_EXPLICIT_SCHED`；
- 明确将监控线程设置为 `SCHED_OTHER`；
- 不让打印线程与 EtherCAT 线程竞争实时优先级。

# 三、多线程快照设计是本次修复最值得深挖的部分

## 8. “只做结构体拷贝”不等于线程安全

假设实时线程写：

```cpp
snapshot_ = current_status;
```

监控线程同时读：

```cpp
auto status = snapshot_;
```

如果没有锁、原子变量或其他同步机制，那么即使 `snapshot_` 只是普通 POD 结构体，也可能产生 C++ data race。

后果包括：

- 读取到一半新数据、一半旧数据；
- 不同字段属于不同控制周期；
- 64 位字段在部分平台出现撕裂；
- 编译器基于“程序不存在 data race”的假设进行重排；
- 整个程序进入未定义行为。

因此，快照设计至少要保证两件事：

1. 实时线程不会被监控线程阻塞；
2. 监控线程能读到一致快照。

------

## 9. 不建议让实时线程竞争普通 `std::mutex`

一种简单方案是：

```cpp
std::mutex snapshot_mutex;
```

实时线程更新快照前加锁，监控线程读取前加锁。

这种做法功能上容易正确，但实时性能有风险：

```cpp
{
    std::lock_guard<std::mutex> lock(snapshot_mutex);
    snapshot_ = current_status;
}
```

若监控线程持锁时被系统抢占，实时线程可能等待它释放锁，从而发生：

- 不可预测阻塞；
- 优先级反转；
- 周期超时。

典型优先级反转过程是：

1. 低优先级监控线程持有 mutex；
2. 高优先级 EtherCAT 线程等待该 mutex；
3. 中优先级线程持续运行；
4. 低优先级线程得不到 CPU，无法释放 mutex；
5. 高优先级线程长期被间接阻塞。

Linux 中可以使用 Priority Inheritance mutex 缓解：

```cpp
pthread_mutexattr_setprotocol(
    &attr,
    PTHREAD_PRIO_INHERIT
);
```

但对高频实时循环而言，最佳方案通常仍是：

> 不让实时线程等待监控线程。

------

## 10. 双缓冲快照是很合适的方案

可以维护两个状态缓冲区：

```cpp
MotorStatusSnapshot buffers_[2];
std::atomic<int> published_index_{0};
```

实时线程始终写未发布的缓冲区：

```cpp
void publish_snapshot(
    const MotorStatusSnapshot& snapshot)
{
    int current =
        published_index_.load(std::memory_order_relaxed);

    int next = 1 - current;

    buffers_[next] = snapshot;

    published_index_.store(
        next,
        std::memory_order_release);
}
```

监控线程读取已发布缓冲区：

```cpp
MotorStatusSnapshot read_snapshot()
{
    int index =
        published_index_.load(std::memory_order_acquire);

    return buffers_[index];
}
```

但是，严格来说，最简单的双缓冲仍需考虑以下竞争：

- 监控线程正在复制旧缓冲区；
- 实时线程经过两次发布后又开始覆盖该缓冲区。

如果监控读取频率远低于发布频率，这种情况并非不可能。因此，更完整的方案包括：

- 三缓冲；
- sequence lock；
- SPSC ring buffer；
- 原子共享指针加预分配对象；
- 带版本号的快照。

------

## 11. Seqlock 很适合“一写多读、允许重试”的监控数据

基本思路：

- 写入前版本号变为奇数；
- 写完后版本号变为偶数；
- 读线程读取前后比较版本号；
- 版本不同或为奇数就重读。

示意实现：

```cpp
class StatusStore {
public:
    void publish(const MotorStatusSnapshot& value)
    {
        sequence_.fetch_add(
            1,
            std::memory_order_acq_rel);  // 变成奇数

        snapshot_ = value;

        sequence_.fetch_add(
            1,
            std::memory_order_release);  // 变成偶数
    }

    MotorStatusSnapshot read() const
    {
        MotorStatusSnapshot result{};

        while (true) {
            const uint64_t before =
                sequence_.load(std::memory_order_acquire);

            if (before & 1U) {
                continue;
            }

            result = snapshot_;

            const uint64_t after =
                sequence_.load(std::memory_order_acquire);

            if (before == after) {
                return result;
            }
        }
    }

private:
    mutable std::atomic<uint64_t> sequence_{0};
    MotorStatusSnapshot snapshot_{};
};
```

不过从严格的 C++ 标准角度看，仅用版本号包围对普通非原子对象的并发读写，仍需要谨慎处理 data race 问题。Linux 内核 seqlock 可以依赖内核内存模型，但用户态 C++ 不能简单照抄。

用户态更稳妥的方式是：

- 使用多个预分配 slot；
- 通过原子索引发布只读 slot；
- 读者通过 reader count 或三缓冲机制防止 slot 被覆盖；
- 或使用成熟的 lock-free/SPSC 数据结构。

这是一个很有含金量的知识点：

> Linux 内核中的并发模式，不一定能直接以同样形式移植到标准 C++ 用户态。

------

## 12. 快照结构应尽量使用固定大小数据

`MotorStatusSnapshot` 中最好只包含：

- 整数；
- 浮点数；
- 枚举；
- 固定大小数组；
- trivially copyable 类型。

尽量不要包含：

- `std::string`
- `std::vector`
- `std::map`
- 拥有堆内存的对象
- 复杂智能指针关系

例如：

```cpp
struct MotorStatusSnapshot {
    int motor_id;
    int step;
    int mode_switch_step;

    bool desired_enabled;

    double actual_position;
    double actual_velocity;
    double actual_torque;

    double tx_target_position;
    double tx_target_velocity;
    double tx_target_torque;

    uint32_t offline_count;
};
```

还可以进行编译期检查：

```cpp
static_assert(
    std::is_trivially_copyable_v<MotorStatusSnapshot>);
```

这样能够降低：

- 动态分配；
- 析构开销；
- 深拷贝；
- 锁竞争；
- 不确定执行时间。

# 四、日志线程与控制线程分离的通用架构

## 13. 控制平面与观测平面应该分离

这次修改体现了一个非常通用的系统设计原则：

### 控制平面

负责：

- EtherCAT receive；
- 状态估计；
- 控制计算；
- 目标下发；
- watchdog；
- 状态机推进。

要求：

- 确定性；
- 低延迟；
- 不阻塞；
- 固定内存；
- 尽可能少的分支和系统调用。

### 观测平面

负责：

- 终端状态显示；
- 日志记录；
- 数据落盘；
- 网络遥测；
- 调试信息；
- 性能统计。

允许：

- 较低频率；
- 数据丢失；
- 显示延迟；
- 使用普通线程；
- 失败后不影响控制。

核心原则是：

> 监控系统可以看不到一次状态，但不能因为监控而阻塞控制系统。

这不仅适用于机器人，也适用于：

- 高频交易；
- 音视频处理；
- 工业 PLC；
- 网络数据平面；
- 游戏引擎；
- 自动驾驶；
- 传感器采集程序。

------

## 14. 更通用的实时日志模式：无锁队列加日志线程

若未来不仅要打印最新状态，还需要保留事件日志，可采用：

```text
实时线程
   ↓
预分配 SPSC Ring Buffer
   ↓
普通日志线程
   ↓
stdout / file / network
```

实时线程只负责：

- 构造固定大小日志记录；
- 尝试压入 ring buffer；
- 队列满时直接丢弃或覆盖；
- 绝不等待日志线程。

伪代码：

```cpp
if (!log_queue.try_push(record)) {
    dropped_log_count.fetch_add(
        1,
        std::memory_order_relaxed);
}
```

这比在实时线程直接打印可靠得多。

SPSC 指：

```text
Single Producer, Single Consumer
单生产者、单消费者
```

它非常适合：

- 一个实时线程生成日志；
- 一个普通线程消费日志。

# 五、周期线程自身的 Linux 编程知识

## 15. 周期任务应使用绝对时间睡眠，避免累计漂移

不推荐简单写：

```cpp
while (running) {
    do_work();
    usleep(1000);
}
```

因为实际周期变成：

# [ T_{\text{cycle}}

T_{\text{work}}+1\text{ ms}
]

每个周期都会累计漂移。

更好的方式是使用：

```cpp
clock_nanosleep(
    CLOCK_MONOTONIC,
    TIMER_ABSTIME,
    &next_deadline,
    nullptr);
```

逻辑是：

```cpp
timespec next = now();

while (running) {
    next = add_ns(next, 1'000'000);

    receive();
    update();
    send();

    clock_nanosleep(
        CLOCK_MONOTONIC,
        TIMER_ABSTIME,
        &next,
        nullptr);
}
```

绝对时间周期控制的优点：

- 不累计工作耗时造成的漂移；
- 可明确判断是否错过 deadline；
- 更容易统计 jitter；
- 更适合固定频率控制任务。

------

## 16. 应显式统计周期超时

只看机器人“动不动”是不够的。建议实时线程维护：

- 当前周期耗时；
- 最大周期耗时；
- 平均周期耗时；
- 超过 1 ms 的次数；
- 连续超时次数；
- 最近一次超时发生时间；
- receive/update/send 分阶段耗时。

例如：

```cpp
struct RealtimeStats {
    uint64_t cycle_count;
    uint64_t deadline_miss_count;
    uint64_t consecutive_miss_count;

    int64_t last_cycle_ns;
    int64_t max_cycle_ns;
};
```

判断：

```cpp
if (cycle_duration_ns > 1'000'000) {
    ++deadline_miss_count;
    ++consecutive_miss_count;
} else {
    consecutive_miss_count = 0;
}
```

实时系统中，平均值往往会掩盖问题。更有价值的是：

- max；
- p99；
- p99.9；
- deadline miss count。

------

## 17. 内存缺页也会破坏实时性

即便代码没有打印，也可能因为 page fault 出现长尾延迟。

常见处理方式：

```cpp
mlockall(MCL_CURRENT | MCL_FUTURE);
```

作用是防止当前及未来映射的内存页被换出。

但仅调用 `mlockall()` 还不够，通常还需要：

- 在进入实时循环前完成内存分配；
- 预触碰线程栈；
- 预初始化容器；
- 禁止实时期间扩容；
- 检查 `RLIMIT_MEMLOCK`；
- 处理 `mlockall()` 失败返回值。

例如：

```cpp
if (mlockall(MCL_CURRENT | MCL_FUTURE) != 0) {
    std::cerr
        << "mlockall failed: "
        << std::strerror(errno)
        << '\n';
}
```

------

## 18. CPU 亲和性可以降低调度抖动

可以通过：

```cpp
pthread_setaffinity_np()
```

将 EtherCAT 实时线程绑定到专用 CPU 核心。

目的包括：

- 减少线程跨核迁移；
- 减少 cache miss；
- 避免与 GUI、日志线程竞争；
- 降低 scheduler jitter。

例如：

```cpp
cpu_set_t cpu_set;
CPU_ZERO(&cpu_set);
CPU_SET(3, &cpu_set);

int rc = pthread_setaffinity_np(
    pthread_self(),
    sizeof(cpu_set),
    &cpu_set);
```

不过 CPU affinity 不是越多越好。错误绑定也可能造成：

- 中断和实时线程挤在同一核心；
- EtherCAT 网卡 IRQ 在其他核心，增加跨核通信；
- 实时线程与内核 housekeeping 任务竞争。

更深入的实时部署还会涉及：

- IRQ affinity；
- `isolcpus`；
- `nohz_full`；
- `rcu_nocbs`；
- PREEMPT_RT 内核。

这些属于进一步优化，而不是本次问题的首要修复。

# 六、线程生命周期也是高频故障来源

## 19. 监控线程必须有完整的启动与退出逻辑

新增监控线程后，需要检查：

- 是否只启动一次；
- `print_motors_info=false` 时是否不启动或保持休眠；
- 析构时是否通知退出；
- 是否调用 `join()`；
- 是否可能访问已经析构的 `_motors` 或 snapshot；
- 配置动态变化时是否会重复创建线程。

典型结构：

```cpp
std::atomic<bool> monitor_running_{false};
std::thread monitor_thread_;
```

启动：

```cpp
void MYACTUA::start_monitor()
{
    bool expected = false;

    if (!monitor_running_.compare_exchange_strong(
            expected,
            true)) {
        return;
    }

    monitor_thread_ = std::thread(
        &MYACTUA::monitor_thread_func,
        this);
}
```

退出：

```cpp
void MYACTUA::stop_monitor()
{
    monitor_running_.store(
        false,
        std::memory_order_release);

    if (monitor_thread_.joinable()) {
        monitor_thread_.join();
    }
}
```

析构函数应先停止线程，再释放线程读取的数据。

错误顺序：

```text
先析构 motors
再停止 monitor
```

可能产生 use-after-free。

正确顺序：

```text
通知 monitor 退出
join monitor
停止实时线程
释放 motors 和其他资源
```

具体顺序还取决于监控线程和实时线程各自访问哪些对象。

------

## 20. 监控线程的 sleep 也要能及时退出

若直接写：

```cpp
std::this_thread::sleep_for(
    std::chrono::seconds(10));
```

析构时可能需要等待很久。

5 Hz 监控对应 200 ms，一般问题不大，但更规范的方式是使用：

- 短周期 sleep；
- condition variable；
- stop token；
- `std::jthread`。

C++20 可以使用：

```cpp
std::jthread monitor_thread_;
```

配合：

```cpp
void monitor_thread_func(
    std::stop_token stop_token);
```

这样生命周期管理更安全。

但 condition variable 和 `jthread` 应只用于普通监控线程，不能让实时线程依赖这些阻塞设施。

# 七、配置语义和接口设计知识

## 21. `{-1}` 代表“全部”属于 sentinel value 设计

`print_motor_ids={-1}` 表示打印全部电机，这是典型的 sentinel value，即哨兵值。

这种设计要特别注意：

- 注释和实际行为一致；
- `{-1, 1, 2}` 如何处理；
- 空集合表示“不打印”还是“全部”；
- 非法电机 ID 是否忽略或报错；
- 是否允许重复 ID；
- 配置是否在初始化阶段一次性规范化。

推荐在非实时初始化阶段展开：

```cpp
if (ids.size() == 1 && ids[0] == -1) {
    ids = all_motor_ids();
}
```

随后：

- 排序；
- 去重；
- 校验；
- 保存为最终 ID 列表。

不要在 1 kHz 实时线程中每周期判断：

```cpp
if (ids contains -1) ...
```

配置解析属于冷路径，不应放到实时热路径。

# 八、故障定位方法本身也很有价值

## 22. `/dev/null` 对照实验属于变量隔离

旧版本运行：

```bash
./policy_test > /dev/null
```

若机器人恢复响应，说明问题与输出路径高度相关。

这个实验隔离了：

- 终端渲染；
- ANSI 清屏；
- 大量文本显示；
- 伪终端处理速度。

但它不能百分之百证明唯一原因，因为：

- `printf` 格式化仍然存在；
- glibc 锁仍可能存在；
- `write()` 仍会调用，只是 `/dev/null` 很快；
- 修改输出环境可能改变线程时序。

因此，严谨表述应是：

> `/dev/null` 实验能提供很强的因果证据，但最好结合周期延迟统计或系统调用追踪进一步确认。

------

## 23. `strace` 可以直接观察实时线程是否执行 `write()`

例如：

```bash
strace -f \
  -e trace=write,writev,ioctl \
  ./policy_test
```

重点观察：

- 哪个线程调用 `write()`；
- 写入频率；
- 单次写入大小；
- 是否有长时间停顿；
- 是否存在 TTY `ioctl()`。

不过 `strace` 本身会显著扰动实时程序，因此：

- 适合验证调用路径；
- 不适合测量真实周期性能；
- 上机时应谨慎使用。

------

## 24. 静态确认“不存在打印路径”不能只看一个函数

“确认 `rt_thread_func()` 中没有 `printf`”还不够，因为它调用的下层函数可能继续打印：

```text
rt_thread_func()
  └── update()
       └── motor.update()
            └── error_handler()
                 └── printf()
```

因此需要检查完整调用链：

```bash
grep -RInE \
'printf|fprintf|puts|std::cout|std::cerr|fflush|write\(' \
src/motors
```

还要关注：

- 日志宏；
- 异常处理；
- assert；
- 第三方库调试输出；
- 错误路径打印。

尤其是“只在异常时打印”仍可能破坏实时性，因为异常发生时往往恰恰是系统最需要稳定控制的时候。

更合理的做法是：

- 实时线程设置错误码；
- 增加计数器；
- 将错误事件推入无锁队列；
- 由普通线程打印。

# 九、本次修改中应优先复查的五个问题

## 第一，快照到底如何同步

这是最重要的二次检查项。

需要确认：

- `get_status()` 是否持锁；
- 实时线程写 snapshot 时是否可能阻塞；
- 监控线程是否可能读到撕裂数据；
- 快照是否包含非 trivially-copyable 类型；
- snapshot 是否使用正确的原子发布机制。

“只读快照”只说明访问对象变了，不说明并发问题已经解决。

------

## 第二，监控线程是否明确为普通线程

检查：

- 调度策略是否为 `SCHED_OTHER`；
- 是否可能继承 `SCHED_FIFO`；
- 是否绑定到与实时线程相同的 CPU；
- 是否可能高频占用 stdout 锁；
- 是否有动态配置导致多个监控线程同时启动。

------

## 第三，实时线程调用链中是否完全没有日志

不仅检查：

```cpp
rt_thread_func()
```

还要检查：

- `receive()`
- `update()`
- `send()`
- 状态机切换函数
- 错误处理函数
- 驱动库 callback
- watchdog 路径

实时线程中留下一个异常打印路径，仍然可能造成长尾抖动。

------

## 第四，是否记录了周期 deadline miss

仅观察：

- `OFFLINE_CNT`
- `STEP`
- `TX_TARGET`

还不足以直接证明实时周期稳定。

建议增加：

```text
CYCLE_US
MAX_CYCLE_US
DEADLINE_MISS
CONSECUTIVE_MISS
RX_US
UPDATE_US
TX_US
```

这样可以直接看到打印开启前后实时性能是否发生变化。

------

## 第五，`SCHED_FIFO` 失败后程序如何处理

当前增加 warning 是必要的，但还需决定：

- 失败后继续运行还是终止；
- 测试模式和实机模式是否采用不同策略；
- 是否允许无实时权限运行真实机器人；
- warning 是否只打印一次；
- 是否验证了最终实际调度策略。

对实机部署而言，无实时调度权限可能不应该只是一条容易被忽略的 warning。

## 机器人部署中高含金量知识

1. 1 kHz 周期任务的 WCET 与 deadline；
2. 实时线程中禁止阻塞 I/O；
3. 控制平面与观测平面隔离；

9. 周期 jitter 的 p99.9/max 统计；
10. EtherCAT watchdog 与周期超时之间的对应关系。

## 本次问题最值得形成的工程结论

可以把经验归纳成一句规则：

> EtherCAT 实时线程只负责收包、计算和发包；所有打印、落盘、网络遥测和复杂诊断均通过预分配快照或无锁队列交给普通线程，任何监控功能失效都不得反向影响控制周期。

这比“不要在实时线程里调用 `printf`”更完整，因为真正需要建立的是一套 **非侵入式可观测性（non-intrusive observability）** 架构。
