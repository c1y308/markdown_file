# P3 步态相位观测：设计、奖励、训练与部署

本文记录 P3 行走任务中新加入的步态相位观测，包括相位的设计方式、相关奖励、训练端的观测拼接方式，以及实机部署端应如何生成完全一致的输入。

## 1. 为什么加入步态相位

仅使用机身姿态、关节状态、速度指令和上一时刻动作时，策略需要自己从历史观测中推断当前处于步态周期的哪个阶段。这可能产生以下问题：

- 左右脚切换时间不稳定；
- 低速时容易碎步或长期双脚着地；
- 不同 episode 的步态频率差异较大；
- 奖励能够约束接触状态，但策略不知道当前期望哪只脚处于支撑期。

因此加入一个周期性的步态时钟，明确告诉策略当前位于步态周期的哪个位置。这个时钟不依赖额外传感器，只依赖策略控制步数和固定控制周期。

## 2. 步态相位如何设计

### 2.1 基本相位

当前步态周期设置为：

```text
period = 0.74 s
```

仿真物理周期为：

```text
sim.dt = 0.005 s
```

每个策略动作保持 4 个物理步：

```text
decimation = 4
step_dt = sim.dt × decimation = 0.02 s
```

因此一个完整步态周期约包含：

```text
0.74 / 0.02 = 37 个策略控制步
```

归一化全局相位定义为：

```text
global_phase =
    ((episode_step × step_dt) mod period) / period
```

其中 `global_phase` 的范围为 `[0, 1)`。

训练端实现位于：

```text
source/unitree_rl_lab/unitree_rl_lab/tasks/locomotion/mdp/observations.py
```

对应代码：

```python
def gait_phase(env: ManagerBasedRLEnv, period: float) -> torch.Tensor:
    global_phase = (env.episode_length_buf * env.step_dt) % period / period

    phase = torch.zeros(env.num_envs, 2, device=env.device)
    phase[:, 0] = torch.sin(global_phase * torch.pi * 2.0)
    phase[:, 1] = torch.cos(global_phase * torch.pi * 2.0)
    return phase
```

### 2.2 为什么使用 sin/cos

不能直接把 `[0, 1)` 的标量相位作为观测，因为一个周期结束时，相位会从接近 `1` 突然跳回 `0`。数值上这是一次很大的跳变，但在物理意义上这两个时刻实际相邻。

因此使用：

```text
phase_sin = sin(2π × global_phase)
phase_cos = cos(2π × global_phase)
```

这样相位在周期边界处保持连续，并且两个值可以唯一表示周期位置。

典型值如下：

| 周期位置 | phase_sin | phase_cos |
|---|---:|---:|
| 0% | 0 | 1 |
| 25% | 1 | 0 |
| 50% | 0 | -1 |
| 75% | -1 | 0 |
| 回到100% | 0 | 1 |

episode 重置时 `episode_length_buf=0`，所以相位从 `[0, 1]` 开始。

## 3. 步态奖励如何给

步态相位观测只告诉策略“现在处于周期的什么位置”。真正定义期望接触状态的是 `feet_gait` 奖励。

### 3.1 左右脚接触时序

P3 配置位于：

```text
source/unitree_rl_lab/unitree_rl_lab/tasks/locomotion/robots/p3/velocity_env_walk_x_cfg.py
```

当前参数为：

```python
gait = RewTerm(
    func=mdp.feet_gait,
    weight=0.35,
    params={
        "period": 0.74,
        "offset": [0.0, 0.5],
        "threshold": 0.58,
        "command_name": "base_velocity",
        "sensor_cfg": SceneEntityCfg(
            "contact_forces",
            body_names=FOOT_BODY_NAMES,
        ),
    },
)
```

每只脚的局部相位为：

```text
leg_phase[i] = (global_phase + offset[i]) mod 1
```

两只脚使用：

```text
offset = [0.0, 0.5]
```

这表示第二只脚比第一只脚错开半个周期，形成左右交替步态。

期望支撑状态为：

```text
is_stance = leg_phase < 0.58
```

所以每只脚约有步态周期的 58% 处于期望支撑期，42% 处于期望摆动期。由于支撑比例略大于50%，左右脚切换附近存在短暂双支撑区，更适合双足机器人稳定换脚。

### 3.2 接触匹配奖励

`feet_gait` 实现位于：

```text
source/unitree_rl_lab/unitree_rl_lab/tasks/locomotion/mdp/rewards.py
```

它将期望支撑状态和接触传感器的实际状态进行比较：

```python
is_contact = current_contact_time > 0
is_stance = leg_phase < threshold
matched_contacts += ~(is_stance ^ is_contact)
```

原始奖励为：

```text
reward = 2 × matched_feet / number_of_feet - 1
```

对于两只脚：

| 匹配脚数 | 原始奖励 |
|---:|---:|
| 2 | +1 |
| 1 | 0 |
| 0 | -1 |

然后乘以配置权重：

```text
gait weight = 0.35
```

代码还使用速度指令做门控：

```python
cmd_norm = torch.norm(command)
reward *= cmd_norm > 0.1
```

也就是说，只有存在有效运动指令时才使用周期接触奖励。原地站立时不会强迫机器人按照相位交替抬脚。

奖励进行了零中心处理。长期双脚着地无法在整个周期中持续获得正奖励，从而避免策略通过站着不走来利用接触奖励。

### 3.3 为什么还需要抬脚高度和悬空奖励

`feet_gait` 只关心“该接触时是否接触、该摆动时是否离地”，不直接规定脚应该抬多高，也不直接限制悬空时间。因此当前任务还同时使用以下奖励。

#### 正常抬脚高度

```text
feet_clearance weight = +0.35
目标鞋底离地高度 = 0.045 m
std = 0.035 m
sole_offset = 0.0408 m
```

奖励近似为：

```text
height_reward =
    exp(-(foot_clearance - 0.045)^2 / 0.035^2)
    × tanh(2 × horizontal_foot_speed)
```

只有脚在水平方向运动、并且速度指令模长大于 `0.1` 时，才能明显获得该奖励。这样不会鼓励机器人原地把脚悬在目标高度。

#### 正常悬空时间

```text
feet_air_time weight = +0.7
threshold = 0.30 s
```

该奖励鼓励形成有效摆动，而不是脚刚离地就立即落回地面。

#### 防止抬脚过高

```text
feet_height_limit weight = -0.20
最大鞋底离地高度 = 0.10 m
std = 0.04 m
```

鞋底高度不超过 `0.10 m` 时惩罚为零，超过后使用归一化平方惩罚：

```text
penalty = ((foot_height - 0.10) / 0.04)^2
```

#### 防止悬空过久

```text
feet_air_time_limit weight = -0.15
最大连续悬空时间 = 0.45 s
std = 0.15 s
```

连续悬空时间不超过 `0.45 s` 时惩罚为零，超过后使用平方惩罚。

#### 其他配套约束

- `feet_slide=-0.12`：抑制接触地面时滑脚；
- `feet_stumble=-0.4`：抑制脚部侧向碰撞或绊倒；
- `air_time_variance=-0.25`：抑制左右脚悬空时间严重不对称；
- `feet_contact_without_cmd=+0.2`：无运动指令时鼓励双脚接触地面；
- `feet_too_near=-0.4`：防止两脚距离过近；
- `undesired_contacts=-3.0`：惩罚脚以外的非期望身体接触。

因此当前设计不是只依赖一个动作幅值惩罚来限制步态，而是同时约束：

```text
接触时序 + 正常抬脚高度 + 正常悬空时间
+ 过高限制 + 过久限制 + 滑脚和异常接触
```

## 4. 训练端如何加入观测

### 4.1 Policy观测

训练端配置位于：

```text
source/unitree_rl_lab/unitree_rl_lab/tasks/locomotion/robots/p3/velocity_env_walk_x_cfg.py
```

`gait_phase` 被放在速度指令和关节位置之间：

```python
class PolicyCfg(ObsGroup):
    base_ang_vel = ObsTerm(...)
    projected_gravity = ObsTerm(...)
    velocity_commands = ObsTerm(...)
    gait_phase = ObsTerm(
        func=mdp.gait_phase,
        params={"period": 0.74},
        clip=(-1.0, 1.0),
    )
    joint_pos_rel = ObsTerm(...)
    joint_vel_rel = ObsTerm(...)
    last_action = ObsTerm(...)

    def __post_init__(self):
        self.history_length = 5
        self.enable_corruption = True
        self.concatenate_terms = True
```

单帧 Policy 观测维度为：

| 观测项 | 单帧维度 |
|---|---:|
| `base_ang_vel` | 3 |
| `projected_gravity` | 3 |
| `velocity_commands` | 3 |
| `gait_phase` | 2 |
| `joint_pos_rel` | 12 |
| `joint_vel_rel` | 12 |
| `last_action` | 12 |
| 合计 | 47 |

由于每个观测项使用5帧历史：

```text
Policy输入维度 = 47 × 5 = 235
```

未加入相位前为：

```text
(47 - 2) × 5 = 225
```

所以新增维度为：

```text
2维相位 × 5帧历史 = 10维
```

### 4.2 Policy输入的准确排列

IsaacLab 会先为每个观测项分别保存5帧历史，再按照配置顺序拼接所有观测项。每项历史内部按“最旧帧到最新帧”排列。

最终235维输入排列为：

```text
[0:15]      base_ang_vel，5 × 3
[15:30]     projected_gravity，5 × 3
[30:45]     velocity_commands，5 × 3
[45:55]     gait_phase，5 × 2
[55:115]    joint_pos_rel，5 × 12
[115:175]   joint_vel_rel，5 × 12
[175:235]   last_action，5 × 12
```

这里不是将完整的47维单帧观测连续重复5次，而是每个观测项先展开自己的历史，再进行项间拼接。部署端必须保持相同规则。

### 4.3 Critic观测

Critic 在 Policy 观测基础上额外使用3维真实机身线速度：

```text
base_lin_vel：3维 × 5帧 = 15维
```

所以：

```text
Critic输入维度 = 235 + 15 = 250
```

Critic 只用于训练，实机部署只需要构造235维 Policy 输入。

### 4.4 配置自动导出

训练脚本在创建训练日志时调用：

```python
export_deploy_cfg(env.unwrapped, log_dir)
```

导出逻辑位于：

```text
source/unitree_rl_lab/unitree_rl_lab/utils/export_deploy_cfg.py
```

它按照训练环境中 Policy 观测项的实际顺序生成：

```text
训练日志目录/params/deploy.yaml
```

生成的 P3 配置中应包含：

```yaml
gait_phase:
  params: {period: 0.74}
  clip: [-1.0, 1.0]
  scale: [1.0, 1.0]
  history_length: 5
```

不要在部署时手工改变这个 YAML 中的观测顺序，否则 ONNX 输入虽然仍可能是235维，但每个区间的物理含义会错位。

## 5. 部署端代码如何加入

### 5.1 在通用观测库中注册 gait_phase

部署端实现位置：

```text
deploy/include/isaaclab/envs/mdp/observations/observations.h
```

加入：

```cpp
REGISTER_OBSERVATION(gait_phase)
{
    const float period = params["period"].as<float>();
    const float global_phase = std::fmod(
        static_cast<float>(env->episode_length)
            * env->step_dt / period,
        1.0f
    );

    std::vector<float> obs(2);
    obs[0] = std::sin(global_phase * 2.0f * static_cast<float>(M_PI));
    obs[1] = std::cos(global_phase * 2.0f * static_cast<float>(M_PI));
    return obs;
}
```

该函数名必须与 `deploy.yaml` 中的键完全相同：

```text
gait_phase
```

P3 的 `State_RLBase.cpp` 只需要包含通用观测头文件：

```cpp
#include "isaaclab/envs/mdp/observations/observations.h"
```

不应在 `State_RLBase.cpp` 中再次手工向输入向量插入相位，否则会造成重复输入或顺序错误。

### 5.2 在部署环境中保存控制步数

部署环境类位于：

```text
deploy/include/isaaclab/envs/manager_based_rl_env.h
```

需要有：

```cpp
float step_dt;
long episode_length = 0;
```

构造时从 `deploy.yaml` 读取控制周期：

```cpp
this->step_dt = cfg["step_dt"].as<float>();
```

策略状态启动或重置时：

```cpp
episode_length = 0;
```

每完成一次策略推理后：

```cpp
episode_length += 1;
```

不要使用物理电机线程的循环次数计算相位。相位必须按照策略推理周期推进；当前策略周期是20 ms，而电机或通信线程可能采用更高频率。

### 5.3 推荐的严格对齐调用顺序

训练环境第一次推理使用：

```text
episode_step = 0
phase = [0, 1]
```

为了让实机首次推理完全一致，推荐部署端使用以下顺序：

```cpp
void step()
{
    robot->update();

    // 当前 episode_length 对应本次策略输入。
    auto obs = observation_manager->compute();
    auto action = alg->act(obs);
    action_manager->process_action(action);

    // 本次推理完成后再推进相位。
    episode_length += 1;
}
```

当前仓库代码是在 `compute()` 之前执行 `episode_length += 1`，这会使首次部署推理使用第1步相位，而训练首次推理使用第0步相位，相差一个策略周期，即20 ms。通常影响不大，但建议按上面的顺序修改以实现严格一致。

### 5.4 历史缓冲无需手工实现第二遍

通用部署端的 `ObservationManager` 位于：

```text
deploy/include/isaaclab/manager/observation_manager.h
```

它会读取每个观测项的：

```yaml
history_length: 5
```

然后完成：

1. 调用 `gait_phase()` 得到当前2维相位；
2. 将当前相位加入该观测项的历史队列；
3. 保留最近5帧；
4. 按最旧帧到最新帧展开为10维；
5. 按 YAML 顺序和其他观测项拼接。

重置时，历史缓冲会用第一次观测填满，而不是用未初始化数据。因此相位历史初始为5份 `[0, 1]`。

部署端不要再单独维护另一套235维总观测历史，否则容易形成与训练不同的“整帧历史排列”。

## 6. 策略模型和部署配置

训练脚本会生成：

```text
训练目录/params/deploy.yaml
```

播放策略时会导出：

```text
训练目录/exported/policy.onnx
训练目录/exported/policy.pt
```

C++部署程序需要同时加载同一次训练对应的：

```text
params/deploy.yaml
exported/policy.onnx
```

不能将235维新策略与旧的225维 `deploy.yaml` 混用，也不能将旧策略与包含 `gait_phase` 的新配置混用。

当前仓库还没有独立的：

```text
deploy/robots/p3
```

实际部署 P3 时，应从现有机器人部署目录移植出 `deploy/robots/p3`，并配置正确的：

- P3 底层通信消息类型；
- 12个关节的 SDK 编号；
- 训练顺序和实机顺序之间的 `joint_ids_map`；
- 默认关节角；
- KP/KD；
- 状态机和安全保护；
- P3 策略日志目录。

步态相位函数本身放在通用 `observations.h` 中即可，不需要为 P3 再复制一份。

## 7. 部署一致性检查清单

部署前至少检查以下项目：

- ONNX输入维度为235；
- `deploy.yaml` 中存在 `gait_phase`；
- `period` 为 `0.74`；
- `step_dt` 为 `0.02`；
- `gait_phase` 位于 `velocity_commands` 和 `joint_pos_rel` 之间；
- 每个观测项的 `history_length` 都为5；
- 历史排列为每项独立的“最旧到最新”；
- 相位只随策略推理次数推进，不随电机通信线程推进；
- 策略重新启动时相位计数器清零；
- 首次推理使用第0步相位 `[0, 1]`；
- 实机12个关节的排列与 `joint_ids_map` 一致；
- `last_action` 保存的是神经网络上一周期的原始动作，而不是电机最终位置；
- 使用与 ONNX 同一次训练生成的 `deploy.yaml`。

如果任意一项不一致，即使输入总长度仍然是235，策略也可能出现明显异常动作。
